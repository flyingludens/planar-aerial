# Mosaic 调查板 — 设计稿

日期：2026-10-25
状态：已与作者逐节讨论并确认（数据模型、提案流、模型配置、UI 四节均已通过）

## 目标

给写作面板增加一个「Mosaic 调查板」：帮助作者梳理故事背景并持续保持其与手稿一致。它管理角色、形式化的角色关系、世界观设定（含梗概、物品），在关键节点（章节写完后）由 AI 产出变更提案、作者审核后更新，并使用独立可配置的 AI 模型（`mosaic` 角色）。整体形态与隐喻参考跑团 GM 屏：一块从底部弹出的大卡片，右侧书签栏切换子页面。

非目标（第一版不做）：

- 后台自动检查手稿——只做作者手动触发的「检查本章」
- 任意嵌套的认知（认知只允许一层）
- 按动作细分模型配置
- 关系/设定的时间区间建模（用当前态 + 变更日志替代）
- chat 借道修改调查板——改墙只有提案-审核一条路
- 关系网画布的拖拽编辑关系/实体——第一版只做查看 + 点边看详情，编辑走表单和提案审核

## 1. 数据模型（属性图）

存储位置：每本书的 `book.json`，新增与 `nodes` 平级的 `mosaic` 字段。

```jsonc
{
  "schemaVersion": 1,
  "nodes": [ /* 现有手稿树 */ ],
  "mosaic": {
    "schemaVersion": 1,
    "entities": [
      {
        "id": "e-<uuid>",
        "kind": "character",            // 受控词表: character | card
        "name": "张三",
        "role": "主角",                  // 一句话定位
        "summary": "外貌、口头禅等自由描述",
        "tags": ["青帮"],
        "statuses": [                   // 仅 character
          { "id": "s-<uuid>", "label": "受伤" }
        ],
        "layout": { "x": 120, "y": 80 } // 关系网画布位置，缺失时自动网格排列
      },
      {
        "id": "e-<uuid>",
        "kind": "card",
        "category": "地点",              // 自由文本: 地点/物品/规则/事件/势力…
        "name": "老宅",
        "body": "卡片正文",
        "tags": [],
        "layout": null
      }
    ],
    "edges": [
      {
        "id": "r-<uuid>",
        "from": "e-a",                  // 实体 id，指向必须存在
        "to": "e-b",
        "truth": { "kind": "挚友", "note": "1937年冬结拜" },
        "beliefs": [                    // 角色主观认知，一层，不嵌套
          { "holderId": "e-b", "kind": "仇人", "note": "李四不知道结拜真相" }
        ],
        "retired": false,               // 作废不删除，默认隐藏
        "log": [                        // 系统在提案采纳时自动追加
          { "at": 1792850000000, "what": "truth.updated",
            "before": { "kind": "陌生" }, "after": { "kind": "挚友" } }
        ]
      }
    ]
  }
}
```

设计取舍（讨论中已确认）：

- **真相 + 认知两层**：每条关系边有作者认定的 `truth`，加上各角色的 `beliefs`（谁以为这段关系是什么）。AI 可生成 beliefs 草稿，作者采纳才算数；AI 开关只控制它能否自动生成草稿。
- **`kind` 用自由文本而非枚举**：中文关系词（结拜兄弟/监视/欠债）无法预设枚举，硬枚举会逼作者曲就。语义归并交给「摘要归并」动作建议，不做硬约束。
- **卡片是自由卡片**：`category` 自由文本，不按类别锁 schema。
- **当前态 + 变更日志**：边只存当前状态，历史变化由采纳提案时自动追加的 `log` 记录，回溯看日志。
- **物品的持有者是边**：物品卡与角色实体之间用 `持有` 关系的边表达，转移即 retire 旧边 + 增新边，关系网上一眼可见。
- **梗概不属于墙**：每章一句话摘要挂在手稿树节点的 `summary` 字段，由 AI 生成、作者可改，与墙的摘要机制一同被读取。
- **角色卡字段**：`role`（一句话定位）与 `summary`（外貌、口头禅等自由描述）即角色卡固定区；`statuses` 是 TRPG 式状态标记，仅 character 实体有。
- **防御性读取**：无效边（端点不存在）读取时丢弃，重复/空 id 重写为 uuid，与现有 `lib/model.js` 的 `uniqueIds` 思路一致。

配套提案 op 扩展（见第 2 节）：`status.add` / `status.remove`（角色状态标记）。

## 2. 提案与更新流

AI 不直接改库。所有变更以提案形式呈现，逐条采纳/驳回/编辑后采纳；未采纳不落数据。

```jsonc
// 提案不落盘：存在于内存/UI 待审队列，采纳结果写进 mosaic
{
  "id": "pr-<uuid>",
  "sourceChapterId": "c-<uuid>",
  "evidence": "那晚他把刀递给我时手在抖",   // 正文原句引文，供作者核对
  "changes": [
    { "op": "edge.upsert",   "from": "e-a", "to": "e-b", "truth": { "kind": "同盟" } },
    { "op": "belief.add",    "edgeId": "r-x", "holderId": "e-b", "kind": "信任" },
    { "op": "entity.upsert", "kind": "card", "category": "地点", "name": "码头仓库", "body": "…" },
    { "op": "status.add",    "entityId": "e-a", "label": "受伤" },
    { "op": "status.remove", "entityId": "e-a", "label": "潜伏" },
    { "op": "edge.retire",   "edgeId": "r-x", "reason": "第4章决裂" }
  ]
}
```

流程：

1. 作者在章节编辑器点「检查本章」（仅手动触发）。
2. 请求带：当前章节正文 + mosaic 紧凑摘要（实体名单 + 边的 kind，不带全文，控制 token）。
3. AI 返回结构化 changes；解析失败或 schema 不符则整单作废并报错，不产生半截提案。
4. 每条 change 展示为一张卡片：出处引句 + 变更前后对照。作者可逐条采纳、驳回、或在卡片上直接编辑后采纳（如把 AI 写的「好友」改成「挚友」）。
5. `edge.retire` 不删数据：边标 `retired: true` 保留，画布默认隐藏，日志记原因。
6. 提案可留半批不处理；下次「检查本章」的提示带上未处理提案数。

## 3. AI 模型配置与动作

- 复用 host 的 roleModels 机制：`/meta` 返回的 `roles` 新增 `mosaic` 角色；作者在模型页指定模型。未在模型页单独指定时回退会话默认模型（与其它角色一致），调查板 AI 入口保持可用。
- 所有动作共用 `mosaic` 角色，第一版不按动作细分。
- 调用层复用 `lib/llm.js`，新增 `mosaic` 系列请求类型（与 suggest/critique 同级），走 wire 契约并做响应校验。

| 动作 | 输入 | 输出 |
|---|---|---|
| 检查本章 | 章节正文 + mosaic 摘要 | 结构化提案 changes（第 2 节 schema） |
| 问答 | 作者问题 + mosaic 当前态 + 相关章节文本 | 依据当前态的回答，引用实体/边 id 作出处 |
| 摘要归并 | 所有边的 kind 文本清单 | 归并建议（如「密友/挚友/好友 → 亲密度」），只建议不改数据；采纳后是 `edge.upsert` 改 kind |

## 4. UI

**打开方式**：从底部向上弹出的一整块大圆角卡片（bottom sheet），覆盖面板主体；顶部窄标题栏（书名 + 关闭），ESC 或点标题栏关闭。

**右侧书签栏**：竖排书签式按钮贴右缘，当前页高亮伸出；待审提案徽标挂在「关系网」书签上。

| 书签 | 内容 |
|---|---|
| 关系网（主页） | 人物关系总览：实体卡片 + 连线画布（位置存 `layout`），点边看真相/认知/日志 |
| 梗概 | 每章一句话摘要列表，AI 生成、作者可改；是 chat 常驻上下文来源之一 |
| 世界观 | 规则、地点、势力等自由分类卡片 |
| 角色 | TRPG 式角色卡（见下） |
| 物品 | 物品卡：描述 + 持有者（即 `持有` 边）+ 出现章节 |

**角色卡**：上半固定区（姓名、一句话定位、外貌、口头禅），下半**状态区**——可勾选的小标记（受伤、怀疑、醉酒、潜伏…），来源两种：作者手动勾，或「检查本章」提案建议（带正文引句）。

**跑团隐喻的落点**：角色状态即 status effects；物品有归属且转移可见；问答即 GM 检定（「第三章的张三知道李四的住址吗」「这条规则和第 5 章矛盾吗」）。

**chat 的背景上下文**（两层）：

1. **常驻摘要**：进入 chat 会话时自动注入 mosaic 紧凑摘要（实体名单 + 每条边 kind 一行式，几百 token 内）+ 梗概，chat 永远知道谁是谁。
2. **临时查**：新增只读故事工具 `story_mosaic_query`（类似 `story_read`），chat 按需查询——按实体名查它的边和 beliefs、按关键词搜卡片正文。工具调用过程对作者可见。工具只读，改墙只有提案一条路。

## 组件边界

| 单元 | 职责 | 依赖 |
|---|---|---|
| `lib/mosaic.js` | mosaic 图的归一化、校验、提案应用的纯函数；不碰 IO | `node:crypto`（uuid） |
| `lib/llm.js` 扩展 | mosaic 系列请求类型 + 响应 schema 校验 | 现有 llm 通道 |
| host 路由扩展 | `story_mosaic_query` 只读工具；`/meta` roles 增加 `mosaic` | `lib/store.js` |
| `client.js` 调查板 | bottom sheet、书签子页、提案审核 UI、画布 | `lib/mosaic.js`、api |

测试沿用现有模式：`mosaic.test.js`（纯函数）、`mosaic-tools.test.js`（工具与 wire 契约）、`client` 相关测试覆盖提案审核与画布渲染。
